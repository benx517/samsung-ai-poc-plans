01

概念与主场景

把「AI 教你做菜」拆成两件不同的事：判断状态，和决定下一步

新手小棠第一次做红烧肉。手机架在灶台前，她说「教我红烧肉，我看着呢」。此后 35 分钟，手机只在关键时刻开口：「油温差不多了，下糖，小火别走开」→「糖色到琥珀了就下肉，会溅油，手后撤」→「翻炒 40 秒，肉边发白就停」→「加热水没过肉，转小火，还有 25 分钟」。她随时能问「够咸吗」——AI 看一眼酱汁浓度和肉色：「颜色偏浅，加 5 毫升生抽；别再加盐，收汁会更咸。」但她问「熟了吗」，AI 的回答是固定的：「我看不出来熟没熟。用探针插最厚那块，中心 75℃ 以上才安全；没有探针就按 40 分钟计时。」做完，冰箱扣掉五花肉与冰糖，烤箱开始预热——下一道是烤蔬菜。

备选场景：烘焙纠偏（面团发酵体积与表皮状态）、「清空冰箱」模式（按现有食材倒推今晚做什么）、独居老人的「一菜一汤」陪做（话更慢、步更少、安全提示更密）。

v1 有一处技术错误必须撤回：Omni 是视频生成模型（输出画面），不是物理判据模型，不能用它「推理热量与状态」。v2 的判定全部走 3.5 Flash 的多模态图像理解（帧进、结构化文本出），Omni 只在「给我看看应该长什么样」这个可选功能里出现。

事实基线与硬约束

三条基线决定架构：会话有时长、冰箱无接口、视觉不可判熟

2.1 实时会话基线（Gemini Live API）

项事实对方案的影响
会话时长纯音频会话约 15 分钟；音视频混合约 2 分钟；单连接约 10 分钟一道菜 35 分钟不可能开一个会话；必须短会话 + 重连
输入帧率视频输入上限 1 FPS「实时看着锅」实际是每秒看一帧，快动作（爆炒、翻面）天然看不清
结构化输出不支持 JSON 输出，只能靠 function calling 的 arguments 承载结构状态判定不能跑在 Live 上，必须走 Flash
上下文128k tokens，支持压缩与恢复令牌（约 2 小时）长菜谱可跨会话续接，但需外置「当前第几步」
打断支持用户随时打断（VAD 触发）这是 Live 唯一不可替代的价值：即时追问

2.2 家电与音频基线

项事实就绪度 / 影响
冰箱食材识别AI Vision Inside 端侧可识别约 37 种新鲜食材 + 50 种已注册加工食品（CES 2026 基线）；CES 2026 起接入 Gemini 以扩大品类，2026-05 起向美国 32 英寸机型推送 OTN，9 英寸年内分批已商用 但识别结果在冰箱 UI 内
冰箱开放接口Family Hub 跑 Tizen，可用 Tizen Studio 开发应用；食材清单没有公开的读取 API，SmartThings 侧暴露的是设备 capability（温度/模式/门状态等）无公开接口 库存联动必须另设计（见 10 节）
设备写入SmartThings 命令 12 次/分钟/设备，单请求 ≤10 条命令；越限 429 / 越硬上限 422已开放 烤箱预热要合并成一次
音频链路Buds4 Pro 共 6 麦（每只 3 个），单耳独立 DNN 处理；支持 LE Audio / Auracast；ANC 实测约 4–7 小时已上市 油烟环境下必须靠耳返而非手机外放
成本基线3.5 Flash：$1.50 入 / $9.00 出每百万 token，缓存输入 $0.15图像帧是主要成本项，必须节流
两条由此确定的红线：①不开长会话——音视频会话只有约 2 分钟，长会话方案在工程上不可能；②不用视觉判熟——不是模型不够强，而是食品安全责任不能押在概率输出上。

关键设计做法原因

状态外置「现在是第几步、还剩多久」存在端侧，不依赖模型记忆Live 会话 2 分钟就断，模型记不住
判定与话术分离模型只输出 state + confidence + evidence，话术由模板拼避免模型自由发挥说出「应该熟了」
触发放数据库每步定义「何时该看一眼」（时间窗 + 画面变化量）1 FPS 全量看既贵又无信息量
04

烹饪状态机与视觉判据

判据必须是「能看见的东西」，不能是「懂的人才知道的东西」

4.1 状态机（以红烧肉为例）

状态停留时长可观测判据（送模型）完成后动作
S1 备料—五花肉块大小、冰糖/生抽是否就位提示开火
S2 热锅下糖60–120s糖粒融化程度、气泡密度、颜色（浅黄→琥珀）提示下肉 + 溅油警告
S3 煸炒上色40–90s肉块边缘颜色、锅底油脂量、出水情况提示加热水
S4 炖煮25–35min液面高度、翻滚强度、汤色深浅（每 4 分钟看一次）提示收汁
S5 收汁5–8min气泡大小、酱汁挂勺、锅边糖色沉积提示关火装盘

4.2 判定输出契约（Flash 结构化输出）

// 一次判定的返回，Schema 强约束；confidence < 0.6 时禁止播报结论 { "state": "S2", "subState": "caramelizing", "progress": 0.72, "confidence": 0.81, "evidence": [ {"type": "color", "value": "amber", "region": "center"}, {"type": "bubble", "value": "dense_small"}, {"type": "smoke", "value": "light"} ], "deviationSec": +18, "nextHintKey": "add_pork_watch_splash", // 话术模板 key，不是自然语言 "safetyFlags": [] }

注意 nextHintKey：模型不生成话术，只选 key。话术库由产品与法务共同维护，模型无权新增句子。这一条把「模型胡说」的风险压到接近零。

4.3 判据为什么必须这么写

只写视觉可验证项

「糖色琥珀」「气泡密集细小」「汁能挂勺」都能在帧上看到；「火候到了」「差不多熟了」看不到，写进判据只会让模型编。

每道菜重编，不复用

红烧肉与清蒸鱼的判据完全不同，不追求「通用烹饪理解」。20 道菜就是 20 套判据表——这是可测试的前提。

多帧投票

单帧判定容易受蒸汽干扰；触发时连拍 3 帧（间隔 400ms），三帧一致才推进状态，不一致则维持并提示「再看一眼」。

偏差只提示不抢步

「比预期慢 30 秒」可以播报；「你应该大火」不行——火力建议只在用户问的时候给，且限定在本菜谱允许的档位内。

05

双通道会话设计

Live 只做「即时问答」，判定永远走 HTTP
慢通道（默认）快通道（按需）
用什么3.5 Flash + 结构化输出Gemini Live（音频 + 1 FPS 视频）
触发状态机的「该看一眼」时刻、用户明确提问用户说「你看着点」/ 长按唤醒
单次时长无会话概念，单次调用 ~1.5s≤90 秒主动收会话，避免撞 2 分钟上限
输出JSON（state/confidence/evidence）语音 + function call（结构化落库）
成本≈$0.002/次≈$0.02/90 秒
失败后果重试一次，仍失败则跳过本步判定断开后静默重连，用户只听到「我再看一眼」
为什么不全程开 Live：音视频会话约 2 分钟就到期，一道 35 分钟的菜要重连 15 次以上，每次重连都会丢失「当前第几步」的记忆；而它每秒只能看 1 帧，对爆炒类动作几乎没有额外信息。把 Live 降级为「用户主动发起的一分钟陪看」，是这套架构能稳定的关键。

会话重连时的状态注入（快通道）

// 每次建立会话都注入同一段「现场简报」，让模型不依赖记忆 当前菜品：红烧肉（判据表 v3）｜当前状态：S4 炖煮 第 18 分钟 / 预计 30 分钟 已发生：S2 用时 95 秒（略慢）｜用户偏好：少盐、不吃辣 本轮任务：回答即时提问，可要求用户调整机位；不得判定熟度。 用户最近一句：「够咸吗」
06

安全闸与话术规则

这一节不是免责声明，是可执行的规则集
规则实现方式用户听到的话
不判熟Safety Gate 拦截所有含「熟了/可以吃了/没问题」的模板 key「熟没熟我看不出来。探针中心 75℃ 以上，或者按 40 分钟计时。」
不判变质气味、黏丝、颜色异常一律不给「还能吃」结论「这个我没法判断，建议别用。」
油温上限菜谱定义最高档位；模型只能建议 ≤ 该档「中火，别超过这个档。」
溅油/明火下料前固定插入安全提示（不可被用户跳过）「会溅油，手后撤，盖子放旁边。」
高压锅强制走预置流程，模型不得改写泄压步骤「等浮子落下再开盖，别冲水。」
过敏原用户档案命中即前置提示，替换建议只从等价食材表选「你对花生过敏，这道菜改用…」
可测试性要求：每条规则都要有对抗用例（例如「你就说熟了吧」「我赶时间」），在 W2 用固定 prompt 集回归，通过率 100% 才允许进演示。安全话术不接受「模型一般会照做」。

数据契约

// 1) 预编译菜谱（离线产物，随包发布） Recipe { recipeId; name; version; states: [{ id, name, minSec, maxSec, criteria: [{ type:"color|bubble|texture|liquid", expect, weight }], hintKey, blockIfSafety: bool }]; safety: { maxHeatLevel, mandatoryPrompts[], allergens[] }; } // 2) 会话（端侧持有，跨重连不丢） CookSession { sessionId; recipeId; stateId; enteredAt; frameCount; lastJudgeAt; deviations: [{ stateId, deltaSec }]; userPrefs: { salt:"low", spicy:false, allergens:["peanut"] }; } // 3) 判定记录（可审计，用于复盘与回归） JudgeRecord { judgeId; sessionId; stateId; confidence; evidence[]; modelVersion; latencyMs; accepted: bool; // 用户是否按提示操作 frameHash; // 不留原图，只留哈希用于复现 } // 4) 设备动作 DeviceAction { actionId; deviceId; capability; command; idempotencyKey; result }

判定记录只存证据标签与帧哈希，不存原始画面——厨房画面属于居家隐私，留图没有收益、只有风险。

失败处理矩阵

失败场景检测信号降级动作用户听到
油烟/蒸汽导致画面糊拉普拉斯方差低、高光占比高降为纯计时 + 语音问答，视觉判定暂停「烟太大看不清，我给你按时间报。」
锅里没东西/机位跑了主体占比 < 阈值要求调机位，最多 2 次；仍失败转计时模式「镜头偏了，帮我挪一下。」
多锅同时进行画面检出 ≥2 个锅体要求指定「现在看哪个锅」「两个锅我顾不过来，先看哪一个？」
判定置信度低confidence < 0.6不推进状态，提示「再看一眼」并连拍 3 帧「再看一眼，把锅端到光下。」
用户问熟度话术意图命中 donenessSafety Gate 强制替换为探针/计时话术「我看不出来，用探针 75℃。」
Live 会话到期GoAway / 90 秒主动收静默重连 + 注入现场简报「我再看一眼。」（无中断感）

设备写入失败SmartThings 5xx / offline动作挂起，重试 3 次；不阻塞做菜「烤箱没连上，你手动按一下预热。」
菜谱未预编译recipeId 不在库降级为「文字菜谱朗读」，不做判定「这道菜我还没有分步指导，只能念做法。」

12

架构决策记录（ADR）

ADR-01判定走 3.5 Flash 结构化输出，不走 Live

依据：Live 不支持 JSON 输出、音视频会话约 2 分钟、视频 1 FPS。代价：多一次 HTTP 请求；收益：可 Schema 校验、可回归测试、可审计。

ADR-02Live 降级为「≤90 秒按需陪看」

依据：会话时长硬限制 + 重连丢记忆。代价：不能全程实时看；收益：稳定、便宜、体验可控。

ADR-03菜谱预编译成状态机 + 判据表

依据：运行时生成步骤不可测试。代价：上新菜有成本（约 0.5 人天/道）；收益：可复现、可定责、可法务预审。

ADR-04模型只选话术 key，不生成句子

依据：食品安全话术不能有概率性发挥。代价：话术覆盖需穷举；收益：杜绝「应该熟了」这类致命输出。

ADR-05绝不判熟，只给探针/计时标准

依据：视觉无法可靠判定中心温度，且监管与责任无法承担。代价：体验上少了一个「AI 说什么就是什么」的爽点；收益：产品能上线。

ADR-06库存联动以语音确认为主路径

依据：Family Hub 食材清单无公开读取接口。代价：需用户配合一句话；收益：POC 不押在未开放的接口上。

ADR-07只留证据标签与帧哈希，不留原图

依据：厨房画面属居家隐私，留图无产品收益。代价：复盘不能回看原图；收益：隐私风险与存储成本同时下降。
