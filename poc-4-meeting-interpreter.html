01

概念与主场景

先承认「谁在说」是有上限的，再谈怎么做得比别人好

周一的跨国例会，东京、北京、柏林三方混说日/中/英。平板立在桌中央当会议麦克风，中国同事戴着 Buds4 Pro：「山田：来週の納品ですが…（译文入耳：山田说，下周的交付……）」——译文前面挂着说话人名字，因为会前每个人都用 5 秒录了一句声纹。讲到专业处，平板双栏滚动原文与译文，点任意一句能回跳录音位置。散会 60 秒，纪要已就绪：决议 3 条、待办 5 条（谁 / 做什么 / 什么时候前）、术语表 12 条（「SKU 补货周期」全文统一译法）。待办一键写入各人日历——但置信度低的待办只标「待确认」，不自动写。

备选场景：跨国客服坐席（实时辅助应答 + 会后质检）；海外差旅面谈（手机单机模式，仅本人近讲）；线上会议（直接吃系统音频轨，拾音问题消失，是最容易做对的一种）。

能力边界要写在产品里：「谁在说」靠声纹匹配，不是靠空间定位。已注册的人能认出来；没注册的人只能标「未知发言人」。抢话、咳嗽、笑声会污染归属——这一点在演示时必须说明，否则第一次标错就会被质疑整套系统。
02

事实基线与硬约束

三星现成能力的实测数字，决定了我们不能「直接套用」

2.1 现有 Interpreter 能力与实测表现

项事实对方案的影响
语言官方称覆盖约 22 种语言，含中文（大陆/香港/台湾）、英（澳/印/美/英）、日、韩、德、法、西等中日英三语在覆盖范围内，不必自建翻译模型
算在哪翻译在配对的三星手机上完成，非耳机独立完成；需 One UI 6.1.1 以上会议场景要一台专用手机/平板做计算宿主
延迟媒体实测每次译文有 2–3 秒延迟；被评为「日常够用，重要会议不够」我们的目标不是「更快」，而是「更完整」：多说话人、术语、纪要
交互形态face-to-face 模式：对方对着手机说话，译文进耳机，本人回话由手机外放；模式切换要在手机上点这是「两人轮流」的形态，不适合多人连续讨论
不支持不能翻译录音、不能翻译视频音轨会议录音回放翻译必须自建

2.2 拾音几何（本节是本方案与 v1 的分水岭）

项事实后果
Buds4 Pro 麦克风每只耳机 3 个麦，共 6 个；单耳独立 DNN 处理，两耳之间不交互做降噪与本人语音增强很好，做「房间声源定位」很差
物理间距两耳间距约 15–20cm，且随头部转动麦克风基线太短，只能分辨左右半平面，无法定位多人
说话人距离对方在 1–4 米外，耳机是开放式佩戴远端语音信噪比低，会议室混响直接吃掉清晰度
平板/手机阵列设备放桌面，多麦阵列 + 波束成形，天然对准房间拾音应该由平板做，耳机只做「输出 + 本人近讲」
v1 的「Buds 麦克风阵列做会议室拾音」撤回。正确分工是：平板负责房间拾音（远场、多人），耳机负责播报（私密、不打扰别人），手机负责计算与网络。这样三个设备的物理特性都被用在对的地方。

双栏对照原文/译文 · 点击回跳录音位置

为什么这样分工收益代价

04

音频管线与说话人归属

归属是概率，产品必须允许「不知道」
采集与预处理
平板阵列 16kHz 单声道；端侧做 AGC（自动增益）与轻降噪。不做强降噪——过度降噪会削掉辅音，翻译反而更差。
VAD 与切段
静音 ≥350ms 判句末；连续语音最长 12s 强制切；切点优先落在能量谷，避免切在词中。每段带 seq 与起止时间戳。
声纹匹配
段级 embedding 与会前注册库比对，余弦 ≥0.72 判归属；0.55–0.72 标「可能·低置信」；<0.55 标「未知发言人」。永不硬猜。
连续段合并
同一说话人相邻段间隔 <800ms 则合并为一句，避免译文碎成豆腐块；合并后仍保留原段时间戳用于回跳。
并发翻译
最多 3 段并行；结果按 seq 排序输出，迟到的段直接丢弃不插队——会议场景里「顺序错」比「漏一句」更伤。
播报与上屏
译文进耳机（一句话一条），双栏上屏；说话人名字只在「已注册」时显示，其余显示「未知」。
为什么不追求更高的归属准确率：声纹在 3 米混响下本身就有天花板；把阈值压低会让「猜错的人名」变多，而会议纪要里写错发言人比写「未知」严重得多。这是产品取舍，不是技术妥协。
05

分段翻译与术语一致性

策略做法解决的痛点
上下文注入每段请求携带「上两段原文 + 术语表命中项」，不携带全文段与段之间的指代（「那个方案」）能接上
术语表强制命中术语直接以「术语=固定译法」形式注入；译文返回后做字符串校验同一名词全文译法不一致
二次修正校验不一致时，用 Flash 做一次「只改术语、不改其它」的重写避免整段重译带来的风格漂移
新术语发现高频未登录专名（出现 ≥3 次且被引号/英文标注）提示用户确认译法会前没准备到的词
不译项人名、产品型号、代码标识保留原文「SKU-4471」被翻成中文的灾难
// 术语表注入格式（每段都带，成本极低但效果显著） [TERMS] SKU 补货周期 = SKU replenishment cycle 交付验收 = delivery acceptance 山田太郎 = Yamada Taro // 人名保留原文，不音译 [RULE] 数字、型号、代码标识原样保留；不确定时保留原文而非猜测。

会话生命周期（跨 15 分钟）

项事实约束工程做法
单会话上限纯音频约 15 分钟每 12 分钟主动收会话并重连，避开强制断

纪要结构与待办抽取

纪要的价值不在「全」，在「可核对」
// 3.5 Flash 结构化输出（全文 1 小时约 15–20k token，一次调用） MeetingMinutes { title; date; durationMin; langs: ["ja","zh","en"]; decisions: [{ text, quote, speaker, at }]; // 每条必须带原文引用与时间点 todos: [{ who, what, due, confidence, quote, at }]; // due 缺失则 null，不猜 glossary: [{ term, translation, occurrences }]; openQuestions: [{ text, quote, at }]; risks: [{ text, quote, at }]; }
规则说明
无引用不入纪要每条决议/待办必须能回跳原文；抽不出来的宁可不写
due 不许编原文没提时间就留空，日历侧显示「待确认时间」
who 只认已注册声纹「未知发言人」的待办统一挂到「待认领」列表
自动写入的门槛confidence ≥0.8 且 who 已确认且 due 明确，三者齐备才自动写日历

失败处理矩阵

失败场景检测信号降级动作用户看到/听到
多人抢话段内 embedding 方差大标「多人重叠」，只译主声源，不标归属「（两人同时说话）」
未注册发言人相似度 <0.55标「未知发言人」，纪要里进「待认领」「未知：……」
远场听不清信噪比低于阈值提示「靠近一点/把平板挪到桌子中间」「这句没听清，能重复一下吗？」
会话到期12 分钟主动收 / GoAway静默重连 + 注入简报；缓存顶 1–2 句无感
译文顺序错乱seq 与到达顺序不一致按 seq 重排；迟到超 5 秒丢弃无感（宁可少一句）
术语译法不一致术语表字符串校验失败二次修正；仍失败则保留原文并高亮该词显示原文 + 下划线
专业词大面积误译低置信标记比例 >15%提示「这场专业词多，建议会前导入术语表」会中不打断，会后提示
待办抽取缺 who/dueSchema 校验失败降级为「待认领待办」，不写日历「这 2 条待办需要你补一下负责人」

网络不可用往返超时切离线语言包（若已下载），质量下降但可用「现在用离线翻译，准确率会低一些」
11

隐私与合规

「录音不出端侧」这句话必须说准，不能说过头
真实的数据流

原始录音只存端侧（Knox 加密）；但每一段语音都会上传到云端做翻译——这是云模型翻译的物理事实。付费 API 层默认不将数据用于模型训练，但「上云处理」这件事必须如实告知，不能说成「全程本地」。

会前告知

开始录音前，平板显示明确提示并要求全体确认（一次点击）；与会者名单可查。企业版提供「会议纪要留痕」开关，默认关闭。

保留期

录音默认 7 天自动删除，可设 24 小时；纪要文本长期保留但可单条删除；声纹 embedding 可随时注销，注销后历史归属降级为「未知」。

跨境

跨国会议必然涉及数据出境。企业版需支持指定处理区域（如仅中国大陆节点 / 仅日本节点），并按客户合规要求提供 DPA 与处理记录。

评审时会被问的那一句：「录音会不会被你们拿去训练？」回答要具体：付费 API 通道默认不用于训练；原始音频只存在设备上；云端只处理片段且不落库（关闭存储）；保留期可配。含糊其辞会直接失去企业客户的信任。

ADR-01平板拾音，耳机只做输出

依据：双耳麦克风基线仅 15–20cm、远端 1–4 米、开放式佩戴，物理上无法做房间声源定位。代价：多一台设备与一次摆放引导；收益：远场清晰度与稳定性显著提升。

ADR-02归属只做声纹匹配，不做空间定位

依据：阵列基线不足；混响下 TDOA 不可靠。代价：未注册者只能标「未知」；收益：不会出现「把 A 的话记成 B」这种破坏信任的错误。

ADR-03迟到的段直接丢弃

依据：会议里顺序错比漏一句更伤。代价：极端网络下会缺句；收益：时间线始终可信。

ADR-0412 分钟主动重连，不等 GoAway

依据：纯音频会话约 15 分钟上限。代价：每场 5 次重连开销；收益：用户永远感知不到断点。

ADR-05纪要不写没有原文引用的内容

依据：会议纪要一旦写错，纠正成本远高于漏写。代价：纪要略「薄」；收益：每条都能点回去核对。

ADR-06低置信待办不自动写日历

依据：误建日程会污染他人日历。代价：需要用户手动确认；收益：不会制造「幽灵会议」。

ADR-07如实告知「语音片段上云」

依据：云翻译的物理事实 + 企业合规要求。代价：叙事不如「全程本地」漂亮；收益：经得起法务与客户安全评审。
