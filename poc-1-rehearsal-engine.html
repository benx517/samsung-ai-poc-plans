预演引擎Rehearsal Engine

说一句话，AI 先用世界模型把明天的场景拍给你看：先出 6 张关键帧看板（10 秒内），确认构图后再渲染成 40 秒预演影片；指着某一幕说「风太大」，只重渲那一镜。定稿后由后台智能体把日历、洗烘、购物车、全屋设备一次落位。

01

概念与主场景

体验的关键不是「生成影片」，而是「不用等影片也能拍板」

周五 22:14，用户对 S26 Ultra 说：「明天带朵朵去海边露营」。手机先花 9 秒排出六格关键帧看板：装车、路上、抵达营地、搭天幕、风向突变、收尾回程；每格下面挂着真实数据——风力 3→5 级、14:30 退潮、紫外线 8、日落 18:52。第二格天幕是湿的，因为 AI 记得上周淋过雨，顺手把洗烘空气洗预约到凌晨 2 点。用户指着第五格说「风太大，换湾内营地」——只有这一镜重渲，20 秒出 360p 草稿，确认后替换成 720p。一句「就这样」，他按下「生成影片」，手机放到无线充上，约 2 分钟后通知栏弹出 40 秒成片；同一时刻日历、闹钟、购物车、手表提醒、洗烘预约全部落位。

备选场景（同一渲染管线复用）：① 新家软装预演——按真实户型生成四机位漫游；② 旅行行程彩排——把签证/天气/机酒冲突演成「会出问题的那一天」；③ 门店销售——给客户演一遍「你家阳台放这台机器人的样子」。

v1 的两处假设在这里撤回。①Omni 单条只能生成 3–10 秒，扩展链累计上限 40 秒，所以「一段长片」在工程上不存在，必须按分镜片做；②单镜 720p 实际耗时 40 秒–3 分钟，所以「说一句话 30 秒出全片」不成立，交互必须改成先看板、后渲染。

04

分镜合约与生成管线

先把「镜头」定义成数据，再谈生成

4.1 六镜合约（40 秒 / 6 镜 / 每镜 5–8 秒）

#镜头时长必须携带的真实数据画面基准
1出发·装车6s出发时刻、气温、装备清单 diff后备箱俯视，天幕/帐篷/保温箱位置固定
2路上5s车程、路况、中途补给点车内视角，后排儿童座椅
3抵达营地8s营地坐标、风力、潮汐、日落时刻第一人称走向营位，海平面在画右
4搭天幕7s风向角、地面类型、日照低机位，天幕杆与地钉可见
5风险时刻6s阵风峰值、降雨概率、退潮时间同一机位，光影明显变化
6收尾·回程8s撤离时刻、垃圾/装备清点夕阳侧逆光，车尾箱关闭

合计 40 秒，正好等于 Omni 续接链的累计上限——但工程上仍然按 6 个独立 job 生成，这样才能只换第 5 镜而不动其它。

4.2 管线八步

端侧意图与槽位抽取
Spark 端侧先判「是不是规划类」；是则抽 时间/同行人/地点/预算/禁忌 五个槽位。缺关键槽位就地追问，不带着空洞往下走。<300ms
数据并联取数
按坐标与时段并发查：天气（含阵风）、潮汐、紫外线、路况；同时读 SmartThings 设备状态与日历冲突。取数失败不阻塞，标记 data_gap 并在看板上显式标注。
Planner 出六镜脚本
3.5 Flash 按 JSON Schema 输出 ShotSpec[6]：镜头、时长、机位、画风、需要注入的数字。Schema 里 durationSec 限定 3–10 的整数，从根上防止生成非法时长。
Guard 对账
脚本里的每个数字必须能追到某次 API 返回；对不上就回退该字段并重跑一次。高危建议（涉水、火源、悬崖）直接改写成保守版本。
关键帧看板
6 张图并发渲染（固定 ref + 固定画风 token）；返回后拼成 2×3 看板，每格叠真实数据。P50 9s / P90 15s。此刻用户已可拍板。
按需渲染影片
用户点「生成」后，只提交被改过的镜头 + 未缓存的镜头；队列并发 3 路，720p，单镜 40–90s。
拼接与叠层
端侧 MediaCodec 拼接 + 8 帧交叉淡化（避免硬切跳帧）；旁白走本地 TTS 后配；时间/地点/风力以 Compose 图层叠在播放器上，不烧进画面。
确认即执行
Action Executor 以一次批量调用落位：日历、闹钟、购物车、手表提醒、SmartThings 场景；返回可撤销清单，30 分钟内一键回滚。

4.3 单镜 prompt 契约（示例：第 3 镜）

// 送 Omni 的 user prompt（首轮即锁定全部约束——模型不支持 system instruction） 第一人称视角走向海边营位，傍晚 17:40，低角度侧逆光； 海面在画面右侧，潮水线距离营位约 15 米； 风力 4 级，天幕边缘明显鼓动，沙面有流动纹理； 写实纪录风格，35mm，浅景深，不要任何文字或字幕； // 参考图：ref_char_01（人物外观）、ref_site_01（营地实景） // durationSeconds: 8 · resolution: 720p · aspectRatio: 16:9

注意：数字（17:40 / 15 米 / 4 级）只能来自 Guard 校验过的数据；prompt 里出现「字幕」二字是必须的负向约束，因为模型做文字不可靠。

05

一致性控制四层

让六镜看起来像同一天、同一个地方、同一个人
① 角色一致性：固定 reference set

开拍前先生成一组「定妆图」（正面/侧面/背面/衣着细节），全片 6 镜复用同一组 ref（上限 10 张用满 4–6 张）；不使用文字描述角色，因为文字每次都会漂。跨镜一致性靠 ref，不靠 prompt。

② 场景一致性：首帧 + 空间锚

营地三镜（3/4/5）共用同一张「营地实景首帧」作为首帧输入，机位与海平面方位写死在 prompt 里。第 5 镜用第 3 镜的尾帧做首帧，保证「同一位置、时间流逝」而非「换了个地方」。

③ 物理一致性：数字显式注入

风力、潮汐、日照角全部以数值写进 prompt，并由 Guard 与 API 对账。不写「风有点大」这种形容词——模型无法把它落到画面上，也无法验证。

④ 文字一致性：不烧进画面

官方限制决定片内文字不可信。所有时间地点标签由播放器图层渲染，好处是 100% 准确、可切换语言、可随修改实时更新，也不需要重渲。

06

修改回路（单镜重渲）

「8 秒重生成整片」是做不到的，但「20 秒换一镜」可以
定位受影响镜头
用户说「风太大，换湾内营地」→ 3.5 Flash 输出 {affected:[3,4,5], reason:"营地变更", patch:{site:"湾内"}}。定位只依赖脚本结构，不依赖画面理解。
先重出关键帧
受影响 3 镜先重渲关键帧（约 6–10 秒），用户在看板上确认「就是这个湾内」再继续。避免花 1 分钟渲出不想要的片子。
360p 草稿验证
确认构图后渲染 360p 草稿（比 720p 快约 60%、成本约 1/3），P50 25s；够用来判断运动与节奏是否对。
720p 替换
草稿通过才上 720p，40–90s/镜；只替换受影响的片段，未受影响镜头直接复用缓存，成本按镜计。
版本与回溯
每次修改生成 cut_vN，保留上一版 72 小时。评审现场改坏了能一键回到上一版——这是演示可靠性的保险丝。
会话状态策略：Omni 的多轮编辑依赖有状态 Interactions 会话（store=false 会断开后续编辑能力）。因此采用「会话内保留、任务结束即删除」：一个 plan 的编辑会话最长 30 分钟，超时后仅保留最终资产，不保留可回溯的编辑链。
07

数据契约

四张结构贯穿全链路；字段缺失必须显式，不许补默认值
// 1) 预演计划（Planner 产出，Schema 强约束） RehearsalPlan { planId: string; // 幂等键，端侧生成 UUIDv7 intent: string; slots: { when, who[], where, budgetCny?, constraints[] }; dataGaps: string[]; // 明确列出没拿到的数据，禁止静默省略 shots: ShotSpec[6]; actions: ActionPlan[]; // 待确认后才执行 revision: int; } // 2) 分镜（每镜一次生成任务） ShotSpec { idx: 1..6; durationSec: 3..10; // Schema 层强制范围 camera: string; style: string; facts: { key: string, value: string, source: "weather|tide|calendar|device" }[]; refImages: string[]; // ≤10 firstFrameAssetId?: string; aspect: "16:9" | "9:16"; } // 3) 片段资产 ClipAsset { clipId; shotIdx; resolution: "360p"|"720p"|"1080p"|"4k"; status: "queued|running|done|failed"; jobId?; attempts; costUsd; generatedAt; checksum; } // 4) 执行计划（可撤销） ActionPlan { actionId; target: "calendar|alarm|cart|watch|smartthings"; payload; idempotencyKey; requiresConfirm: true; undoToken?; executedAt?; }

所有结构走 3.5 Flash 的 JSON Schema 结构化输出，解析失败率应接近 0；渲染任务与文本任务用 planId 关联，便于按 plan 统计成本。

09

失败处理矩阵

演示现场不会给你重试三次的机会
失败场景检测信号降级动作用户看到什么
单镜超时（>6min）job 轮询超时该镜降 360p 重试一次；再失败用关键帧做 Ken Burns 动态该格显示「草稿画质」，其余镜头正常
内容审核拒绝安全过滤返回去掉人物/涉水元素重写该镜 prompt（最多 2 次）「这一镜改成远景，人物不入画」
角色漂移与定妆图 CLIP 相似度 < 阈值重渲 + 增加 ref 权重，最多 2 次；仍漂则该镜改背面/远景无感，或提示「这一镜改成了背影」

隐私与合规

  • AI 生成标识：所有输出带 SynthID 隐形水印；App 内与分享卡片均标注「AI 生成预演，非实拍」，避免被当作真实记录传播。
  • 肖像：不使用真人照片做 ref，默认用生成的定妆形象；若用户上传家人照片，仅本地加密存储、仅在本次任务内使用，任务结束即删。
  • 个人上下文：偏好与家庭记忆走 Personal Data Engine 端侧加密；上云只传本次任务所需的槽位字段（时间/地点/人数），不传通讯录与住址全量。
  • 儿童：场景涉及儿童时不上传可识别人脸，只保留背影/远景；这也是失败矩阵里「角色漂移→改背影」的合规理由。
  • 数据保留：渲染资产默认保留 7 天，用户可即时删除；Omni 编辑会话 30 分钟后不保留可回溯链。
  • 区域：EEA/瑞士/英国不支持上传视频编辑，若在这些区域演示须切纯生成路径（本方案主线已是纯生成，天然兼容）。

12

架构决策记录（ADR）

每条都绑定一个事实依据，便于评审追责
ADR-01以分镜片为单位生成，不做长片

依据：Omni 单条 3–10 秒、续接累计 40 秒上限。代价：需要客户端拼接与音画对齐；收益：可单镜替换、可并发、失败可局部降级。

ADR-02先看板后渲染

依据：单镜 720p 耗时 40 秒–3 分钟。代价：多一次用户确认；收益：把「等待」从必经路径挪到可选路径，评审现场永远不会空场。

ADR-03画面内不烧文字，数据走 UI 叠层

依据：官方模型卡将「画面内文字准确」列为已知限制。代价：成片分享时必须带播放器；收益：数据 100% 准确、可本地化、改数据不用重渲。

ADR-04中文旁白用本地 TTS，不用 Omni 原生音频

依据：Omni 不改声音、语音编辑受限，且中文语调与品牌口吻难控。代价：多一步后配；收益：可改口播稿而不重渲画面。

ADR-0516:9 与 9:16 双队列

依据：Omni 仅支持这两种比例。代价：同一 plan 渲两遍；收益：投屏与手机全屏都原生适配，不裁切。

ADR-06修改走单镜重渲 + 版本回溯

依据：单镜成本可算（720p ≈$0.8/镜），整片重来成本 ×6 且等待翻倍。代价：需要镜头级缓存与版本管理。

ADR-07设备执行全部经服务端，令牌不下端

依据：SmartThings PAT 现仅 24 小时有效、写入限 12 次/分钟/设备。代价：需要服务端；收益：可批量合并、可幂等、可撤销。
