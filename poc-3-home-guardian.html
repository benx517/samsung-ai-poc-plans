01

概念与主场景

单看一个信号毫无意义，叠加起来才是故事

独居的张阿姨最近有些反常：冰箱门连续 3 天几乎没开过（基线日均 14 次，降到 2 次）、电视从每天 4 小时掉到 20 分钟、客厅灯晚上 7 点后没亮过。三个信号单独看都能解释——可能出门了、可能早睡了。但它们同时往下掉，这在过去 90 天里没出现过。系统先在电视上轻声问：「张阿姨，今天身体还好吗？」她说「有点感冒，不想吃」。系统降级为关怀模式，只给女儿发一条不刺眼的消息：「妈妈今天说有点感冒，吃得少，建议晚上打个电话。」第二天冰箱门次数回升，基线自动恢复——系统什么都没再说。

备选场景：养宠家庭（喂食器/饮水机使用异常 + 活动量下降）；有孩家庭（夜间频繁开门 + 客厅灯长亮 → 安全确认）；出差模式（长期无人 → 异常开门提醒）。

先划清边界：这套东西不是跌倒检测，不是急救，不是医疗设备。它监测的是「生活节律的塌陷」，时间尺度是天，不是分钟。任何把宣传口径做成「老人摔倒能报警」的做法，都会在第一次真事故时变成法律责任。

事实基线与硬约束

这一节直接决定了「健康数据不能做主链路」

2.1 设备事件基线（SmartThings）

项事实对方案的影响
订阅机制每个 Installed App 最多 40 条订阅；创建 40 次/15 分钟；单事件 ≤10 KiB只订阅必要 capability；事件里不放自由文本
读取频率设备状态读取 12 次/分钟/设备；推送优先，轮询兜底正常走订阅，断线重连后才补一次全量状态
设备规模单 App 最多 30 台云连接设备一个家庭 5–12 台，够用
规则Rules API：100 条/用户、50 条/Installed App复杂判定放服务端，规则只做简单联动
计费API 自 2026-10 转付费，个人档约 $4.99/月；免费期到 2026 年 9 月底每户每月固定成本，评审预算要列
令牌PAT 现只有 24 小时有效期；生产必须 OAuth服务端 OAuth + 刷新，令牌不下端

2.2 健康数据基线（这是 v1 需要改的地方）

路径能拿到什么门槛与限制
Health Connect步数、心率、睡眠、血氧、体重等标准化记录默认只能读最近 30 天，读更早需历史权限；后台连续采集需后台权限；没有睡眠呼吸暂停记录类型
Health Connect 的数据新鲜度由 Samsung Health 决定何时导出实测同一时刻：App 内 4,566 步 / Health Connect 3,211 步，且只导出了步数、滞后约 90 分钟；应用无法强制它导更多、更快
Samsung Health Data SDK睡眠呼吸暂停、不规则心律通知等专有数据需合作伙伴审批并登记包名 + 签名证书；仅三星设备；未审批只能开发者模式本机测试，否则直接报授权错误
Samsung Health Platform（服务端）运动/睡眠/健康/身体成分等需申请开发者计划，审批约 5–15 个工作日；OAuth 分环境凭据
Health Sensor SDK原始 ECG（500Hz）、按需 PPG（100Hz，单次约 30 秒）、连续 PPG/ACC（25Hz）、皮温、生物阻抗合作伙伴审批；不是本 POC 该碰的东西

监管口径补充：三星睡眠呼吸暂停功能是 FDA De Novo 授权（DEN230041，2024-02-06），并由 2026-07-20 的 K261011 扩展至 18 岁以上并支持 Galaxy Ring；其适应症明确不用于独立诊断、不替代多导睡眠监测。血压功能无 FDA 记录。任何「手表能查出病」的表述都不成立。

结论（v2 的关键调整）：健康数据三条路径全部有审批闸门，且 Health Connect 有 30 天窗口 + 90 分钟级滞后、无法强制刷新。所以健康数据只能做「周级参考」，绝不进触发链路。v1 里「Watch8 心率异常 → 触发预警」的写法撤回。

信号定义与基线算法

每个信号都必须是「事件能数出来」的量，不是「感觉」

4.1 信号清单（首版 6 个）

信号定义数据来源方向性权重
冷藏门开启次数每日 00:00–24:00 门开事件计数冰箱 door capability下降异常1.2
烹饪设备使用灶具/烤箱/微波炉每日运行时长合计SmartThings 运行状态下降异常1.2
电视开机时长每日开机分钟数TV 电源状态双向1.0
夜间照明18:00–24:00 客厅灯累计亮灯分钟灯开关/亮度下降异常1.0
洗衣频次滚动 7 天洗衣完成次数洗衣机运行状态下降异常0.8
手机活跃时段每日首次解锁时间（仅时刻，不看内容）端侧统计推迟异常1.0

刻意不做的信号：摄像头画面、麦克风常听、通讯录与通话对象、位置轨迹、任何健康生理值。理由写在 09 节。

4.2 基线：滚动中位数 + MAD（不用均值）

// 每个信号按 90 天滚动窗口计算；中位数对"偶尔来客人"这类尖峰免疫 median_i = median(x_i[1..90]) mad_i = median(|x_i - median_i|) scale_i = 1.4826 * mad_i + 0.5 // 0.5 防止除零 z_i = (x_i_today - median_i) / scale_i // 只关心"塌陷"方向的信号，取负向偏离；双向信号取绝对值 dev_i = max(0, -z_i - 1.5) // 1.5σ 以内视为正常波动，不产生分数 score = Σ (w_i * dev_i) // 裁剪单信号上限 4.0，防止一个信号主导 activeSignals = count(|z_i| > 2.0)

4.3 触发条件（三条同时成立）

条件 1activeSignals ≥ 2（至少两路同时异常）
条件 2score ≥ 3.0
条件 3连续 2 天成立（避免单日噪声）
冷启动前 14 天只学习不告警
冷却窗口同一家庭 7 天内最多 1 次 L2 询问
免打扰22:30–07:30 不发起 L2（L4 除外）
为什么必须 concurrence：单个冰箱门少开两天，最常见的原因是「出去玩了」。只有两路以上、且跨设备类型同时塌陷，才具备「生活节律改变」的判别力。这条规则会把误报压下一个数量级，代价是漏报——这是刻意的取舍。
05

分级响应与话术

四级，每级都有明确的退出条件
级别触发动作退出条件
L1 记录score ≥3.0 但仅 1 天只写本地日志，不打扰任何人次日恢复即清零
L2 本人询问连续 2 天成立电视/手机语音温和询问，附一句可验证的事实（「这两天冰箱开得少了」）回答「没事」→ 记录负样本，7 天不再问
L3 家属提示L2 后 12 小时无回应，或本人回答「不太舒服」给已授权的家属发一条低强度消息 + 证据链三行家属确认已联系 → 关闭
L4 建议求助L3 后 24 小时仍无任何交互，且信号持续恶化建议家属上门/联系邻里，并提供完整时间线人工关闭

5.1 话术示例（模板化，模型只填数字）

// L2（本人） 「张阿姨，我看您这两天冰箱开得比平时少，是不是不太舒服？没事的话我就不打扰了。」 // L3（家属，微信/短信级，不打电话） 「妈妈这两天做饭和开冰箱都比平时少很多（近 3 天冰箱 2 次，平时 14 次）， 今天问她说有点感冒。建议晚上给她打个电话。」 // 禁止出现的表达 「检测到异常」「健康风险」「可能患病」「建议就医」——一律不出现在产品文案里

话术由产品 + 法务共同维护；模型只允许填 {次数}、{天数} 这类占位符，且数字必须来自同一份证据链。

06

数据契约

// 1) 每日特征（唯一上云的粒度） DailyFeature { householdId; date; signals: [{ key:"fridge_door"|"cooking"|"tv"|"night_light"|"laundry"|"phone_first_unlock", value: number, unit, coverage: 0..1 }]; // coverage = 该设备当天在线比例 } // 2) 基线（端侧持有） Baseline { key; median; mad; sampleDays; updatedAt } // 3) 评估结果 Assessment { assessmentId; householdId; date; score; activeSignals; level: 1..4; evidence: [{ key, today, median, deltaPct, z }]; suppressedReason?: "cold_start"|"cooldown"|"coverage_low"; } // 4) 响应记录（可撤回） ResponseRecord { responseId; assessmentId; level; channel; sentAt; ackAt?; cancelReason? }

coverage 是关键字段：设备离线那天所有信号都会「下降」，如果不按在线比例折算，断网一次就会误报一次。coverage < 0.6 的日子直接不参与判定。

08

失败处理矩阵

失败场景检测信号降级动作用户/家属看到
设备离线导致假下降coverage < 0.6当日不判定，标记「数据不足」无打扰（周报里注明「本周有 2 天数据不全」）
外出旅行全部信号同时归零 + 门锁/位置线索识别为「离家模式」，暂停判定，返回后重新累计无打扰
家里来客人信号上升而非下降只记录不告警（本产品只关心塌陷方向）无打扰
基线漂移（季节变化）连续 14 天中位数单调移动基线按 90 天窗口自动跟随，不做人工干预无打扰
冷启动期异常sampleDays < 14不判定，用群体基线仅作展示参考「还在熟悉您家的作息」
误报被取消本人回答「没事」写入负样本；该组合 7 天内不再触发无打扰
家属未授权无有效授权关系L3 降级为 L2 再问一次，不外发「要不要告诉家人？」
消息通道失败推送回执失败重试 3 次后转短信；仍失败则记录待人工家属端看到「未送达」
模型文案失败结构化返回异常回退到纯模板（只填数字）文案略生硬，但信息完整
09

隐私、伦理与合规

这个产品最容易死在「不被信任」，不是死在技术
不做的事（硬边界）

不装摄像头、不常听麦克风、不读通话记录与通讯录、不取位置轨迹、不做任何疾病判断、不做急救承诺。这些不是「暂不做」，是产品定义的一部分。

双向同意

被照看者本人必须知情并单独同意（中国《个人信息保护法》下行为数据可构成敏感个人信息，需单独同意）；家属侧授权必须由本人授予，且本人可随时一键关闭。不能由子女单方面开通。

数据最小化

上云只有「每日标量」：次数、时长、是否异常。设备级原始事件、时间戳序列全部留在家庭本地；云端连「几点开的冰箱」都看不到。

可退出与可删除

关闭后立即停止采集；删除请求 7 天内清除云侧全部特征与基线；本地数据由用户在设备上清除。周报里明确写「数据只用于这份摘要」。

舆论风险要提前设计：「家电在监控老人」是最容易引爆的叙事。产品对外表述必须是「家电在替家人留意生活节律」，且演示时必须主动说明「我们看不到画面、听不到声音、不知道你几点开的冰箱」——把不可见性做成卖点，而不是等人来质疑。

11

架构决策记录（ADR）

ADR-01主链路只用 SmartThings 行为遥测，健康数据不进判定

依据：Health Connect 默认 30 天窗口且导出滞后、Data SDK 需合作伙伴审批、Platform API 审批 5–15 个工作日。代价：少了「生理指标」叙事；收益：POC 能在 4 周内真正跑起来。

ADR-02用中位数 + MAD，不用均值与标准差

依据：家庭行为分布长尾（来客人、节假日）。代价：对渐变不敏感；收益：尖峰不污染基线。

ADR-03必须两路以上 concurrence 才触发

依据：单信号下降最常见的解释是外出。代价：漏报；收益：误报降一个数量级。

ADR-04模型只写措辞，不改等级

依据：分级影响真实人际关系，不能让概率模型决定要不要通知子女。代价：话术需穷举；收益：可解释、可审计。

ADR-05上云只传每日标量，不传事件序列

依据：时序细节可反推作息与在家人数，属敏感信息。代价：云端无法做细粒度分析；收益：隐私叙事站得住。

ADR-06不做实时告警，不做急救定位

依据：数据链路本身是天级，且急救责任无法承担。代价：失去「安全硬件」定位；收益：不产生致命期望。

ADR-07coverage < 0.6 直接弃判

依据：设备离线会造成系统性「假下降」。代价：可用天数减少；收益：断网不再引发误报。
