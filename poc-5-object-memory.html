01

概念与主场景

它记的是「你告诉过我的东西」，不是「它看到的一切」

周五晚上要出门，护照不见了。用户对手机说「我的护照在哪」——3 秒后：「6 月 12 日 21:40 在书房桌面见过（附照片），之后 38 天没有新记录，置信度中等。最近一次你把它放进书房右手边抽屉。」他说「带我去看看」，手机进 AR 模式：抬头显示「书房 · 前进 4 米」，走到桌前再显示「上次在这里 · 看右手边抽屉」。找到后他举起手机拍一张，说「放这了」——时间线立刻更新，系统顺手记下「这是第 3 次在书房找到护照，建议设个固定位置」。全程没有任何全景照片离开这台手机。

备选场景：出门前物品自检（按行程核查证件/充电器/药盒最近是否在家）；常丢物品周报（钥匙位置变化主动提醒）；家庭共享（配偶也能查到「孩子的疫苗本在哪」，共享范围按物品设）。

v1 的不成立前提：原文写「Jet Bot 建图数据已开放、可控制机器人前往坐标」。核对后事实是：公开的 SmartThings 接口对扫地机只暴露运行状态与开关（samsungce.robotCleanerOperatingState + switch），地图与坐标不在公开 API 内；地图只在 SmartThings App 里可见。机器人的定点清扫也没有公开的坐标级接口。
所以 POC 主线必须换成一个不依赖未开放接口的形态——这也是下面「三源设计」的由来。

事实基线：哪些能拿到

先列接口可达性，再谈能力，顺序不能反

2.1 三类数据源的真实可达性

数据源能拿到什么可达性本 POC 定位
A. 手机拍记用户主动拍摄的照片 + 一句语音 + 房间（手选）完全可控 相机 + 端侧模型，无需任何厂商授权主线，覆盖 100% 场景
B. Jet Bot 巡航画面清扫过程中的前视画面、物体识别结果无公开接口 需合作伙伴通道W3 加分项，拿不到不影响主线
C. Jet Bot 状态事件开始/暂停/回充/故障；可作为「今天家里被清扫过」已开放 SmartThings capability辅助新鲜度信号
D. 扫地机地图/坐标房间划分、坐标、可通行区域不在公开 API 仅 App 内可见不依赖，改用「房间手选 + 照片」

补充事实：SmartThings 官方限流规定设备状态读取 12 次/分钟/设备、单请求最多 10 条命令；扫地机相关 capability 只到「运行状态」层级。「控制机器人走到 (x,y)」这件事，在公开接口层面不存在。

3.1 为什么「拍记」反而是更好的主线

  • 精度更高：用户拍摄时是「特意对准这个物品」，构图、距离、光照都优于机器人路过时的一瞥。
  • 零授权：不依赖任何厂商接口，今天就能在真机上跑通。
  • 隐私更干净：只有用户主动拍的那一张、只有物品附近的裁剪区域，不存在「全屋被扫过一遍」的观感。
  • 可解释：回答永远带「这是你 6 月 12 日拍的」——证据是用户自己产生的，信任成本极低。
代价要认：拍记依赖用户动作，覆盖率不如自动巡检。所以产品定位是「重要的那 30 件东西」（证件、钥匙、遥控器、药盒、充电器），而不是「记住家里所有物品」。这个定位反而让演示更聚焦。
04

登记与识别管线

拍一张的成本要低到「顺手」，否则没人用
一键拍记
锁屏卡片 / 负一屏入口，点一下进相机；拍完自动追问一句「这是什么？放哪了？」——语音回答即可，不要求打字。从点击到保存 ≤15 秒
物品主体检测与裁剪
端侧轻量检测框出主体，裁成 1024×1024 ROI 再上传；不上传整图。这样既省 token（约 1,290/图），也避免把桌面杂物、家人照片带上云。
隐私模糊（上传前）
端侧检测人脸、屏幕、证件号码区域并高斯模糊；模糊失败则拒绝上传并提示重拍。顺序很关键：先模糊、后上传。
识别与描述生成
3.5 Flash 输出结构化结果：物品名、类别、颜色/材质/显著特征（用于后续再识别）、是否与用户口述一致。不一致时以用户口述为准，并记一条 conflict。
房间归属
POC 阶段手选房间（一个大按钮，默认上次房间）；不给「自动判定房间」的假承诺。后续可用蓝牙/Wi-Fi 指纹做建议，但需用户确认。
写入时间线
写一条 sighting：物品 ID、房间、时间、缩略图路径、识别置信度、来源（manual / robot）。同一物品的多次 sighting 按时间倒序索引。

4.1 再识别怎么做（同一件物品的跨时空匹配）

层级方法用途
强匹配用户口述名称 + 类别 + 显著特征文本（如「深蓝封皮、右上角有贴纸」）多数场景足够，且完全可解释
弱匹配图像 embedding 余弦相似（端侧模型）用户说不清特征时的兜底
不匹配相似度低于阈值 → 不说「这是同一个」，只说「同一类物品在附近出现过」避免把「另一本护照」当成「你的护照」
05

检索与衰减模型

寻物场景里，错答案比没答案更糟
// 置信度 = 基础识别置信 × 时间衰减；半衰期按物品"会被移动的频率"分档 halfLife = { 证件: 45d, 钥匙: 21d, 遥控器: 12d, 药盒: 14d, 充电器: 10d, 其他: 20d } conf(t) = baseConf * 0.5 ^ (daysSinceSeen / halfLife[class]) // 新鲜度加成：若当天 Jet Bot 清扫过该房间且未检测到该物品，衰减加速 1.5 倍 // 展示分档（不显示数字，显示人话） conf ≥ 0.70 → 「比较确定」 ｜ 0.40–0.70 → 「可能在这」 conf < 0.40 → 「太久没更新，只能作为线索」
查询类型处理回答形态
「护照在哪」按物品名精确 → 时间倒序 → 取最近时间 + 房间 + 缩略图 + 置信档 + 建议下一步
「我钥匙最近老丢哪」按物品聚合房间频次「近 30 天 7 次里 5 次在玄关，建议放个托盘」
「明天出差要带的都在吗」按行程模板列清单 → 逐项查最近 sighting清单式：✓ 身份证（昨天）｜? 充电器（12 天前）
查不到不编造「没有记录。要不要现在拍一张记下来？」
一条硬规则：超过 2 个半衰期没有新记录时，回答里必须出现「很久没更新」，并且不再给「就在那」的语气。产品宁可显得笨，也不能让用户在错误的地方翻 20 分钟。
06

「带我去看看」AR 引导

不能指挥机器人，就指挥人——而且用照片对照
步骤实现为什么这样做
房间导航手机 AR 模式下显示「书房 · 前进约 4 米」；室内精确定位不做承诺不依赖 UWB 基站与室内地图，只给方位与距离感
到达提示进入目标房间后切换为「上次的位置：桌面右侧」房间级准确率远高于坐标级
照片对照半透明叠加上次拍摄的缩略图，供用户视觉比对人对「当时长什么样」的识别力极强，比任何坐标都可靠
寻找成功一键「放这了」重拍 → 更新 sighting把「找到」变成一次新的、更高质量的数据点
寻找失败提示扩大范围（同房间 → 相邻房间），并记录一次 missmiss 会影响该物品的衰减速度，让下次回答更保守
这个形态反而更适合演示：评审现场拿手机走两步、叠着照片在桌上找到护照——比「让机器人爬过去」更快、更可控，也不依赖未开放的机器人接口。

数据契约

// 1) 登记物品（用户显式创建，永不自动扩充） Item { itemId; name; class: "证件"|"钥匙"|"遥控器"|"药盒"|"充电器"|"其他"; features: string[]; // "深蓝封皮" "右上角贴纸" embeddingRef?; createdAt; sharedWith: userId[]; } // 2) 目击记录（唯一的定位事实） Sighting { sightingId; itemId; roomId; seenAt; source: "manual"|"robot"; thumbPath; // 端侧加密文件路径，不上云 baseConf; // 识别置信 note?: string; // 用户原话 } // 3) 查询结果（回答即证据） Answer { itemId; bestSighting; confBand: "high"|"mid"|"low"; daysSinceSeen; halfLifeDays; missCount; evidence: { thumbPath, roomId, seenAt }; suggestion: "去书房右手边抽屉看看" | "拍一张记下来"; } // 4) 新鲜度信号（来自机器人状态事件，仅作辅助） FreshnessSignal { roomId?; robotCleanedAt; durationMin }

注意 Item 只能由用户创建——这是隐私架构的地基，也是 ADR-01 的依据。

失败处理矩阵

失败场景检测信号降级动作用户看到
物品长期未更新超过 2 个半衰期降为「线索」，语气转保守，建议重拍「太久没更新了，只能当线索」
用户口述与识别冲突类别不一致以用户为准，记 conflict，不提「我认错了」按用户说法保存
相似物品混淆embedding 相似但特征不符不判同一件，只说「同类型在附近出现过」「可能是另一本，你确认下」
隐私模糊失败端侧检测到人脸/证件号未遮住拒绝上传，要求重拍或手动涂抹「这张有隐私信息，重拍一张或涂掉」
房间选错用户事后纠正允许编辑房间；历史 sighting 一并修正「已把这条改成书房」
AR 定位漂移视觉特征不足/光线差退回静态提示（房间 + 照片）「AR 不太准，先看这张照片」
机器人事件缺失无 FreshnessSignal衰减按默认速率，不做加速无感
共享冲突物品未授权给该用户拒绝并提示申请「这件物品未共享给你」
模型不可用超时/熔断仅保存照片与语音，识别延后重试「已记下，稍后补上识别」
10

隐私架构（本方案的核心）

这个产品能成立，全靠「它记的比你想要的少」
只记登记物品

物品列表只能由用户显式创建，系统不自动发现、不自动扩充。看见一只杯子不会记下来——因为这正是「家用摄像头」让人不安的地方。

只传 ROI，不传整图

上传前在端侧裁到 1024×1024 的物品区域，并做人脸/屏幕/证件号模糊。云端从未见过你家的全景。

缩略图不出端

照片加密存在手机本地；云端只回「这是深蓝色封皮的证件」这类文本描述，不存图。换机时数据不迁移，除非用户主动导出。

共享按物品授权

默认不共享；每件物品单独勾选可见成员。共享只共享「位置 + 照片」，不共享历史轨迹。

对外一句话：「它只记得你让它记的东西，照片从不离开这台手机。」这句话既是最强的隐私叙事，也是最容易验证的事实——评审时可以现场断网，除识别外的全链路仍然可用。

12

架构决策记录（ADR）

ADR-01主线用手机拍记，不依赖机器人

依据：公开 API 只暴露扫地机运行状态，地图与坐标不在其中；定点清扫也无可调用接口。代价：需要用户动作；收益：今天就能跑通、精度更高、隐私更干净。

ADR-02只记登记物品，不做通用扫描

依据：通用扫描的隐私观感与合规成本远高于产品价值。代价：覆盖率有限；收益：叙事站得住，评审敢开摄像头演示。

ADR-03上传前裁剪 + 模糊，只传 ROI

依据：整图含大量无关隐私且更贵。代价：端侧多一步处理；收益：token 成本降一个量级，云端无全景。

ADR-04房间手选，不做自动房间判定

依据：室内定位精度不足以可靠判房。代价：用户多点一下；收益：位置准确率可控，不会出现「把它记到邻居家」。

ADR-05置信度用半衰期，且必须显示「很久没更新」

依据：物体会移动，旧记录天然贬值。代价：回答显得没那么「神」；收益：不会把用户引到错误的地方。

ADR-06「带我去看看」用 AR + 照片对照，不指挥机器人

依据：无机器人的坐标级控制接口。代价：需要人走一趟；收益：演示可控、成本低、成功率反而更高。
