01

概念与主场景

上午十点，售后工程师老陈到客户家修一台不制冷的 AI 神冰箱。冰箱在厨房死角，光线差、空间窄，两只手要拿万用表和螺丝刀。他只需要说话：「看一眼前面板」——眼镜自动对焦拍下故障码面板，耳中回应：「E4，启动电容异常。先断电，右侧检修板两颗十字螺丝。」他拆开、说「好了」，下一步才继续。遇到不认识的板子，他说「这个我没见过」，AI 不硬猜，而是要求他重拍：「往左一点，拍主板丝印。」识别后提示：这块不是原厂板，上次被第三方改过——但这句话只在手机上写进备注，不在客户面前播报（见 06 节社交规则）。四十分钟后工单草稿已完成，他改两个字提交，全程手机没出过口袋。

备选场景（同一链路可复用）：① 门店导购——看着顾客旧机型，耳中给换机话术与以旧换新报价；② 物业/保险查勘——第一视角取证 + 现场生成查勘记录；③ C 端延展——自己装家具、修水管的「家庭修东西教练」（去掉工单闭环）。

2.3 模型能力基线（Gemini Live API）——本节是架构的真正分水岭

会话上下文窗口128k tokens
纯音频会话时长约 15 分钟
音频 + 视频会话时长约 2 分钟
单条连接时长约 10 分钟
断开前通知（GoAway）约提前 60 秒
会话恢复令牌有效期2 小时
视频输入帧率1 FPS（建议 768×768）
音频出入格式16kHz PCM 入 / 24kHz PCM 出
图片单次上限3000 张 / 单文件 7MB
结构化 JSON 输出不支持
可用工具function calling / Search / Maps
打断（barge-in）服务端 VAD 自动处理
三条硬约束直接否决了“把摄像头一直开着”：① 音视频混合会话只有约 2 分钟上限，撑不住 40 分钟工单，且 1FPS 对快速手部动作本就无用；② 连续推流会同时打穿 155mAh 电池与室内上行带宽；③ 客户家中持续录像的合规风险不可接受。因此本方案的核心决策是「按需拍关键帧，不推流」（ADR-01）。
另一条容易踩空的事实：Live API 不支持结构化输出，也不能调 countTokens。所以工单结构不能靠“让模型输出 JSON”，必须通过 function calling 的 arguments（带 schema）承载，或在会话结束时交给一次在线 Flash 调用生成（ADR-03）。

来源（2026-10-21 核实）：Samsung Unpacked 2026-07-22 发布资料与多家媒体规格报道；Android Developers「Jetpack XR SDK · 眼镜可用性 / 投影上下文」文档与 DP4 发布说明；Firebase AI Logic「Live API limits and specs / sessions」文档。版本会变，实施前需复核一次。

04

关键接口与代码契约

以下为实施骨架，字段名以官方文档为准

4.1 佩戴态闸门：未佩戴即停采集

// 手机侧常驻服务中，把"能不能采集"变成一条 Flow ProjectedContext.isProjectedDeviceConnected(context, coroutineContext) .flatMapLatest { connected -> if (!connected) return@flatMapLatest flowOf(Lifecycle.State.DESTROYED) val pc = try { ProjectedContext.createProjectedDeviceContext(context) } catch (e: IllegalStateException) { return@flatMapLatest flowOf(Lifecycle.State.DESTROYED) // 上下文随断开失效，须重建 } XrDevice.getCurrentDevice(pc).getLifecycle().currentStateFlow } .collect { state -> when (state) { Lifecycle.State.STARTED -> gate.open() // 已佩戴：允许唤醒词与相机 Lifecycle.State.CREATED -> gate.close() // 未佩戴：释放相机流、停唤醒词 Lifecycle.State.DESTROYED -> session.end() // 断开：结束会话并落盘草稿 } }

注意：每次重连会产生新的 deviceId，旧 ProjectedContext 必须丢弃重建——这是最常见的崩溃源。

4.2 Live 会话建立参数（示意）

{ "model": "gemini-3.1-flash-live-preview", // 以当期可用 Live 模型为准 "responseModalities": ["AUDIO"], "inputAudioTranscription": {}, "outputAudioTranscription": {}, "systemInstruction": "…见 4.4 指令骨架…", "tools": [{ "functionDeclarations": [ …见 4.3… ] }], "contextWindowCompression": { "slidingWindow": { "targetTokens": 32000 } }, "sessionResumption": { "transparent": true }, "speechConfig": { "voiceConfig": { "prebuiltVoiceConfig": { "voiceName": "…" } } } }
  • 必须开压缩：不开压缩 15 分钟就到顶，一次上门要横跨 4 个连接；开启后上下文自动滚动摘要，会话可长期维系。
  • 必须开恢复：10 分钟连接上限 + 室内弱网，重连是常态而非异常；恢复令牌 2 小时有效，足够覆盖一个工单。
  • 音色要选低刺激型：工程师一天听几百句，避免高亢亲和型音色造成疲劳，语速略快于默认。

4.4 system instruction 骨架（要点，非全文）

角色 你是家电维修现场助手，服务对象是持证工程师，不是终端用户。 节奏 一次只给一个动作，每句不超过 15 个字；等他说"好了"再给下一步。 不确定 看不清就说看不清，并给一条取景指令（靠近/换角度/拍丝印），禁止猜测。 依据 任何维修步骤必须来自 lookup_procedure 的返回；没有出处就不说。 禁区 带电作业、制冷剂回收、燃气部件：只播报预置安全规程，并要求手表确认。 社交 涉及第三方改装、客户责任、费用判断的结论，不入耳播报，只写 draft_field_note。 称呼 不用"您好/亲"等客服语；直述，像老师傅在旁边说话。
05

会话生命周期管理

最容易翻车、也最能体现工程深度的一节

5.1 状态机

IDLE ──唤醒词/镜腿长按──▶ ARMED ──"看一眼"──▶ CAPTURING ──帧就绪──▶ THINKING ▲ │ │ │ (摘下/断开) ▼ │ │ SPEAKING │ ▼ │ └──── DESTROYED ◀──── PAUSED ◀──────────────────────────────────── AWAIT_ACK │ ┌──────────"好了"──────────┬─────────"重拍"────┘ ▼ ▼ 下一步（THINKING） CAPTURING │ 低置信 / 高风险 ──▶ ESCALATE ──▶ WRAP_UP ──▶ 工单草稿
  • ARMED 是常态位：只在 ARMED 接受指令；SPEAKING 时靠服务端 VAD 支持打断，但打断后必须回到 AWAIT_ACK 而不是直接执行新任务（防误触发）。
  • PAUSED 不是 IDLE：摘下眼镜是暂停而非结束，回来用恢复令牌续上，避免“摘一下就得重讲”。
  • WRAP_UP 幂等：工单草稿按 draftId 幂等提交，弱网重试不产生重复工单。

5.2 40 分钟工单如何跨过 10 分钟连接上限

触发系统动作用户感知
连接接近 10 分钟（GoAway，提前约 60 秒）预约重连：在模型说完一句后立即用恢复令牌重建，注入会话摘要 + 最近 3 轮一声极短「嘀」，其余无感
室内 Wi-Fi 抖动断连指数退避重连（0.5/1/2/4s，上限 4 次），失败转蜂窝；仍失败降级离线「网络不稳，先查本地手册」
上下文逼近 128k滑动窗口压缩自动生效；后端保留完整会话日志供追溯无感（长工单后期追问细节可能需重述一次）
摘下超过 5 分钟会话挂起并落盘；再戴上提示是否继续「要继续刚才那台冰箱吗」
实测前必须验证的一件事：重连后的“语义连续性”。压缩 + 恢复能保住上下文，但模型对“正在做第 3 步”这种过程状态的记忆会衰减。对策是把过程状态外置：手机侧维护 currentStepIndex，每次重连时以一条文本指令注入（“当前进行到第 3 步：拆检修板”），不依赖模型自己记。
06

无屏交互语法

没有屏幕，就没有“请看提示”

6.1 播报规范

  • 一句一动作，≤15 字；不用编号列表、不念长型号（改说“那个白色小方块”，配件码进手机）
  • 先给结论再给动作：「E4，启动电容。先断电。」
  • 禁止客服语（“您好 / 亲 / 建议您”）；语气对齐老师傅
  • 危险步骤前置一个低音警示音，播完必须等确认

6.2 耳标音（Earcon）——替代视觉反馈

  • 「咔」单响 = 已拍下（对应快门与 LED）
  • 双短音 = 正在查手册
  • 低音下滑 = 看不清，需要重拍
  • 三连上行 = 工单已保存
  • 单长音 = 需要手表手势确认（安全步骤）

6.3 语音指令表（固定 8 个词）

指令语义为什么不做开放意图
看一眼 / 拍照抓帧并送理解现场噪声、方言、客户插话会让开放式意图识别不稳。固定词表把“识别错误”的代价压到最低，并可用端侧关键词匹配兜底；复杂表达交给模型的自然语言能力吸收，不要求用户背命令。
好了 / 下一步确认当前步骤完成
重拍丢弃当前帧，重新取景
再说一遍重播上一句
停立即停止播报
记一下写一条现场备注（含时间戳）
问专家升级远程支持
收工生成工单草稿并结束
最重要的一条产品规则（社交安全）：客户就站在旁边。凡是涉及“这块板被人动过”“这个故障是使用不当造成”“这次要收费”的结论，一律不在耳中播报，只写进手机工单备注。AI 在客户面前说错一句话，损失的不是准确率，是工程师的面子和这单的信任。
另一个必须先解决的现实问题：客户说话会不会被当成指令？会。所以取音必须用 projected context 的佩戴者语音分离能力，把非佩戴者语音从指令通道剥离（仍保留在环境音中用于上下文判断）；再加固定词表 + 唤醒词双门控，误触发率可压到很低。这也正是我们不用蓝牙 HFP 单麦通道的原因（ADR-06）。
07

取景与视觉子系统

触发抓帧
语音「看一眼」或镜腿短按。自动对焦完成后抓单帧（12MP），LED 同步亮、耳标音「咔」——三者共同构成“已拍摄”的确证。
预处理与质量门
长边缩放至 1024px（Live 建议输入 768×768，更大只增 token 不增准确率）；JPEG q80；本地做三项检测：拉普拉斯方差判模糊、高光占比判反光、主体占比判是否对准。任一不过关即不进模型，直接播报取景指令。
上传与理解
关键帧与本轮语音在同一轮内送入会话，让模型同时看到画面与问题；不使用 1FPS 视频流。
置信度分流
提示词要求模型附带 confidence：≥0.8 直接给步骤；0.5–0.8 给结论但要求二次确认；<0.5 不给结论，只给取景指令或升级专家。
重拍闭包
最多连续 3 次重拍；仍失败则强制升级远程专家，避免把工程师困在原地打转——这是现场体验的底线。
多帧投票（仅关键判定）
故障码、丝印、接线位置三类高风险识别，要求连拍 2 帧结果一致才给结论；不一致即视为低置信。
为什么“拍帧”在准确率上反而优于“推流”：1FPS 视频流等于把一张手抖的糊图反复喂给模型；按需抓帧则可以让工程师停下来、对准、等对焦完成——人的配合把图像质量拉上去了。这是无屏设备的隐藏优势。
08

知识与 RAG 子系统

环节做法关键约束
语料维修手册（按机型）、历史工单（近 2 年、结案且评价好）、配件图与爆炸图、安全规程手册需先做版权/授权确认；工单需脱敏（去姓名电话地址）
切分按“步骤”切而不是按字数切：一个可执行步骤 = 一个 chunk；元数据保留机型/故障码/章节号切分粒度错了，RAG 只会返回“一段看起来相关的长文”，无法变成一句听得懂的指令
检索混合检索：故障码/型号走关键词精确匹配，症状描述走向量；结果 rerank 取 top-3故障码必须精确命中，不能被向量相似度带偏
出处强制每条步骤携带 citation{docId, page, section}；无 citation 的条目不进播报这是幻觉的第一道闸
拒答策略无命中时固定话术：「手册里没这条，我帮你叫专家」+ 自动升级宁可承认不知道，也不能给一条“听起来对”的步骤
离线包3 个主力机型的常见故障码表 + 安全规程，打包为本地 SQLite（约 20–40MB）室内弱网、地下车库必备；离线只做检索不做生成
更新知识库每周增量发布；手机端离线包按版本号静默更新新机型上市必须能在一周内进库
这套设计的副产品：每次“无命中 → 升级专家 → 专家解决”的过程，就是一条高质量的新知识。四周内预计积累 20–30 条真实缺口，这本身就是给业务方最有力的证据——不是“AI 很聪明”，而是“AI 把知识缺口暴露出来了”。

安全闸（规则引擎，不交给模型）

等级判定依据系统行为
L0 普通断电状态下的拆装、检测、清洁正常语音指引
L1 需提示涉及水路、玻璃件、重物搬运播报前加一句风险提示，无需确认
L2 需双确认带电检测、制冷剂回收、燃气部件、高压电容只播报预置规程原文（不由模型改写）+ 单长音 + Watch9 手势确认后才继续
L3 禁止引导超出持证范围（如制冷系统焊接）明确拒绝并给出升级路径，不做任何步骤性描述
实现要点：L2/L3 判定在规则引擎内完成——输入是机型号、部件码、命中步骤的标签，输出是等级。模型不参与这一步，也不能通过改写措辞绕过。审计日志记录每次 L2 确认的时间、操作人、确认来源，用于事后追溯。

架构决策记录（ADR）

每条都绑定一个事实依据，便于评审追责
ADR-01按需拍关键帧，不做视频推流

依据：Live API 音视频混合会话仅约 2 分钟、视频输入上限 1FPS；155mAh 电池不支持连续推流；客户家中持续录像合规不可行。代价：丢失连续动作理解，需靠人的配合（停下、对准）。

ADR-02不客户端直连 Live API，走后端代理

依据：密钥生命周期过长不可下发；企业需集中鉴权、计费隔离与审计；2026-11-02 起 Firebase AI Logic 强制 App Check。代价：多一跳（约 20–40ms）与一个常驻服务。

ADR-03结构化数据靠 function calling，不靠模型输出 JSON

依据：Live API 不支持结构化输出。做法：工具参数带 schema 承载结构；工单正文由一次在线 Flash 调用基于会话摘要生成。代价：多一次模型调用与一层参数校验。

ADR-04安全闸用规则引擎，模型无权改写

依据：L2/L3 场景出错不可逆；模型可通过措辞绕过任何提示词约束。代价：需维护一份部件 / 步骤风险标签表。

ADR-05语音为主、手机为辅

依据：本代眼镜无屏（显示版 2027 才有）。做法：耳机输出口语指令，手机承载结构化信息（配件码、照片组、工单）。代价：双设备注意力切换，靠“耳标音 + 手机不打扰”缓解。

ADR-06取音走 projected context，不用蓝牙 HFP

依据：HFP 只给单麦；projected context 可多麦 + 降噪 + 佩戴者语音分离 + 多设备环境下保持录音权。代价：依赖 DP4 预览 API，权限需针对投影设备单独申请。

ADR-07不做“手机常亮替代屏幕”

依据：一旦手机成为主界面，双手占用场景的价值就消失了，方案退化为普通 App。手机只做“事后核对”，不做“事中导航”。
